# P2P 产品化规划

| 状态 | 最后更新 |
| --- | --- |
| 规划稿（Draft） | 2026-08-22 |

## 1. 产品定位

一句话：**P2P 基础设施 + SDK，运营一套统一公共网络**。核心卖点是服务端不碰内容、带宽成本摊给用户网络。

- 对内容分发方：零带宽成本的分发通道（数据面 P2P 直连，服务端只做控制面）
- 对终端：浏览器原生可用（WebRTC 同栈，浏览器与 App 共用）
- 对运营方：控制面中心化、数据面去中心化——管理面可控，数据面免流量

**统一公共网络**：运营一套公共 Tracker / Punch 基础设施，所有客户端（无论来自哪个 App）接入同一网络——同一套身份注册表、同一个资源索引、同一批 Punch 节点。协议文档本就假设 Tracker 为"全网唯一身份真相源"（§3.1.1），统一运营无需改造协议；租户隔离反而会碎片化网络、削弱 P2P 规模效应，因此**不做多租户 SaaS**。

对标路线：WebTorrent（基础设施 + SDK + 公共网络）。

## 2. 交付物全景

产品化交付物分三层：**必须自研的三件套**、**可复用的现成组件**、**文档之外的工程化补充**。

### 2.1 必须自研：核心三件套

| 组件 | 职责 | 为什么不能复用 |
| --- | --- | --- |
| **Tracker Server** | 控制面核心：身份注册表、资源索引（announce / query）、connection 记录、JWT 签发、nonce / jti 一次性语义、revocation（§7.2.1） | 协议完全自定义（Ed25519 身份 + JWT 授权 + info_hash 索引），BT tracker 不适用 |
| **Punch Server** | 信令中继：Binding 维护（join / heartbeat / exit）、常驻与瞬时信道、signal_key 断线恢复、connect JWT 的 jti 消费、容量控制（§7.2.2） | 自定义信令中继，比 STUN/TURN 复杂，无现成组件 |
| **Client SDK** | 身份管理 + 控制面通信 + WebRTC 数据面拼装（§7.3 三张函数面表格的完整实现） | 最大的工程量，见第 3 节 |

### 2.2 可复用组件

- **STUN / TURN**：coturn（协议文档 §4.7 已指定 static-auth-secret 方案）
- **WebRTC 栈**：浏览器原生；App 端用 libwebrtc / WebRTC.framework
- **JWT、Ed25519、bencode**：现成库

### 2.3 工程化补充（协议文档之外的必需物）

1. **运营面**：Tracker / Punch 管理控制台（Punch 清单管理、密钥轮换工具）、监控、审计——分布式基础设施没有运维面无法存活
2. **协议一致性测试套件**：三件套可独立实现，没有 conformance test，协议演进必坏（§7.1 声明消息版本化 schema，但未定义测试）
3. **参考实现客户端**：SDK 无法自证正确，需要至少一个完整参考客户端做互操作验证
4. **横向扩展入口**：负载均衡 / DNS 部署模板（协议契约只暴露逻辑服务地址，落地仍需部署层）
5. **计量服务**：遥测接收、交叉校验、内容归属汇总与账单（第 8 节），商业化的前置组件

## 3. Client SDK 平台与语言面

SDK 是**最重的交付物**，文档 §7.3 的函数面表格只是接口骨架，底下还有：

- 身份管理：Ed25519 密钥对、peer_id 派生、revocation token 生成
- Punch 信道层：常驻 Binding 信道 + 瞬时信令信道 + `signal_key` 断线恢复
- WebRTC 数据面：双 DataChannel、block / piece 状态机（missing → partial → downloaded → verified）、bitfield / have、request / reject / cancel、顺序窗口 + rarest first + endgame 调度、magnet 模式、TURN 回退
- 文件 I/O：in-place 写盘、块哈希校验、bitmap 持久化

| 平台 | 语言 | 说明 |
| --- | --- | --- |
| Web | TypeScript | 浏览器原生 WebRTC，开发最顺，优先做 |
| iOS | Swift + WebRTC.framework | 原生 WebRTC 封装 |
| Android | Kotlin + libwebrtc | 原生 WebRTC 封装 |
| 桌面 | Electron（复用 JS）或原生 | 视目标用户决定 |
| 服务端 / 种子源托管 | Go / Rust | CDN 兜底虚拟 Peer（§5.1 `cdn_list`）的托管实现 |

## 4. 实施路径（MVP）

```
Phase 1：Tracker + Punch + JS SDK + 浏览器 Demo + coturn（复用）
         —— 浏览器原生 WebRTC 免掉 ICE/DTLS 平台差异，专注验证协议闭环
            （控制面 + 消息语义 + 状态机），一个语言跑通全链路
Phase 2：一致性测试套件 + 参考客户端 + 可观测性
         —— 协议稳定性的前提；可观测性覆盖 Tracker/Punch 运营面
Phase 3：iOS / Android SDK + 桌面端
         —— 原生 WebRTC 封装，多平台行为差异处理
Phase 4：公共网络规模运营（多活扩容、SLA、滥用治理、合规）+ 计量服务 + 私有化交付
         —— 商业变现层
```

平台优先序的依据：JS SDK 能用浏览器原生 WebRTC 免掉最复杂的 ICE / DTLS 实现，让 Phase 1 专注验证协议本身，而不是被平台差异拖住。

## 5. 风险与关键点

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| WebRTC 跨平台行为差异 | 不同平台 ICE / DTLS / SCTP 实现行为不一致 | 一致性测试套件 + 参考客户端互操作验证 |
| 状态机与调度正确性 | block / piece 状态机 + endgame / rarest first / 顺序窗口组合是纯逻辑但极易出错 | Phase 1 优先实现并压力测试 |
| 断线重连 | `signal_key` 恢复、瞬时信道补发逻辑（§3.5） | 早期引入网络故障注入测试 |
| 协议演进 | 版本化 schema 定义了机制但未定义治理 | Phase 2 定协议版本策略 |
| 信任根运营 | 全网身份注册表与授权签发握在运营方，是全网信任根 | KMS 级密钥管理、公开公钥、可审计运营（§8 信任模型限定破坏半径） |
| 滥用与合规 | 公共网络 info_hash 索引可能传播盗版 / 恶意文件 | Tracker 不存内容（仅哈希索引）、配合特定 info_hash 下架、服务条款明确网络内容与运营方无关 |
| 冷启动 | 网络规模上来前 P2P 比例低 | SDK 自带 CDN 兜底（§5.1 `cdn_list`），冷启动靠 CDN，规模上来后 P2P 比例自然上升 |

## 6. 商业形态

**公共网络免费开放（获客 / 生态 / 网络效应），收入靠周边能力**——开源模式的镜像：基础设施免费，能力收费。

| 层 | 形态 | 收入 |
| --- | --- | --- |
| 公共网络 | 统一 Tracker / Punch 免费接入 | 0（获客 / 生态层） |
| SDK | 嵌入开发者产品的 P2P 分发能力 | 授权费 + 企业支持合同 |
| 私有化 | 需要自有控制面的信任敏感客户 | 一次性交付 + 年维护 |
| 增值 | 专属节点、质量保障、流量分析、SLA | 订阅 |

成本结构：**人力成本 + 运营成本**（公共网络云成本）。控制面负载轻，运营成本随规模线性但占比低；数据面带宽成本由用户网络承担——单位用户成本随规模递减。

## 7. 定价模型

计费口径：**客户内容（info_hash 集合）经 P2P 送达的下载字节数**——只算下载侧（客户关心的是自己的内容被 P2P 送到多少用户手里），不计上传侧（上传是用户贡献，不向客户收费）。

定价公式：

```
定价 = p × x × P
客户节省 = p × P × (1 − x)
其中：p = 客户全量 CDN 的单价；P = P2P 实际分发的下载带宽（计量见第 8 节）；
      x = 分成比例（0 < x < 1，设计自由度）
```

注意："按 CDN 费用的 x% 收费"必须是对 **P2P 那部分 CDN 费用的分成**，不是对总费用的分成——费率等于 CDN 单价（x=1）时客户净节省为零，没有采用动机。双赢区间是 0 < x < 1：客户省 `(1−x)` 那部分，运营方赚 x 那部分。

数字例子（客户月分发 100TB，p = 0.15 元/GB，P2P 占比 70%，x = 30%）：

| 项 | 金额 |
| --- | --- |
| 全量 CDN | 1.5 万 |
| 运营方收费（0.15 × 0.3 × 70TB） | 0.31 万 |
| CDN 兜底（0.15 × 30TB） | 0.45 万 |
| 客户总成本 | 0.76 万，**省 49%** |

x 的取值逻辑：渗透率（P2P 占比）越高，同样的 x 客户省得越多，可收取更高的 x；冷门内容占比高的客户 P2P 占比低，应自动降 x（或按带宽阶梯定价）。

## 8. 计量设计

**核心约束**：数据面是 P2P 直连，服务端（Tracker / Punch）不在数据路径上——"P2P 实际分发的带宽 P"是服务端天然看不见的量，必须绕道计量。

### 8.1 计量口径

- 按**下载侧**字节数（上传不计费）
- 按**内容归属**汇总：客户注册自己的 info_hash 集合（运营层表：info_hash → 客户账号），账单 = 该集合的 P2P 下载字节数 × p × x

### 8.2 遥测上报

SDK 周期性上报（每会话或每批次）：`(peer_id, info_hash, 对端 peer_id, connection_id, 下载字节数, 时段)`，用 peer_id 私钥签名（复用 login / join 持钥证明模式，带 timestamp 防重放）。端点：Tracker 新增 `POST /telemetry`，会话 JWT 认证，与横向扩展架构（共享存储）兼容。

### 8.3 交叉校验（可信度基石）

单方上报不可信（作弊者少报），但 P2P 下载是双向的：**A 从 B 下载的字节数 ≈ B 上传给 A 的字节数**。

```
A 上报："我从 B（connection_id=X）下载 500MB"
B 上报："我上传给 A（connection_id=X）500MB"（B 是普通用户，无少报动机）
Tracker 配对校验：min(500, 500) = 500MB 采纳
不一致 → 标记可疑 → 抽查 / 审计
```

- Tracker 本就持有 connection 记录（query 签发时生成），天然支持配对
- 普通用户不付费、无利害关系——信任锚从"上报者诚实"转移到"无利害关系对端诚实"，这是 P2P 架构下唯一成立的信任假设

### 8.4 采样与隐私

- **采样**（可选）：SDK 按概率（如 1/10）对会话完整上报、其余只报汇总，总量按抽样比外推——抽样 + 交叉校验组合下，作弊需协同伪造一对连接的数据，成本高于收益
- **计量白名单（必须）**：Tracker 下发付费客户内容白名单，SDK **只对白名单内 info_hash 上报字节数**——普通用户的非客户内容完全不产生遥测，隐私面从"全网下载历史"收敛为"客户内容下载量"（与 §8 的元数据监视风险隔离）

### 8.5 计费链路

```
客户侧：上传内容 → 注册 info_hash 归属（运营层表）
用户侧：SDK 下载 → 只对白名单 info_hash 上报（签名遥测）
Tracker：交叉校验 → 按客户归属汇总 → 月度账单（P2P 分发 GB × p × x）
大客户：月度报表 + 对账流程（客户自持统计 vs 运营方统计，争议仲裁）
```

| 配置 | 精度 | 计量成本 |
| --- | --- | --- |
| 全量上报 + 交叉校验 | 高（±5%） | 每条几十字节，控制面可承受 |
| 抽样 1/10 + 交叉校验 | 中（±15%） | 更低，适合小客户 |
| 大客户 | 高 | 加对账流程，SLA 化 |
